# Cross-host study and identifiability of a learned phase input

The baseline is Stage 3 at commit `69fbd29acdb4eba7961d56176693786b6181477a`. All results below the execution heading are design targets. Only the support witness and condition-grid checks have been executed here.

## A necessary distinction

Every Stage 3 connector training condition has deterministic drift rate zero. For any query interval t the proposed input (cos(ωt), sin(ωt)) is therefore (1,0) throughout training. Conditioning on this constant does not identify a learned extrapolation to a signed rotation. Brownian increments in the generated IQ do not vary the public deterministic rate.

For example let p₊(k|θ) ∝ exp(2 cos(θ − kπ/2)) and p₋(k|θ) ∝ exp(2 cos(−θ − kπ/2)). Both are valid four-sector predictors. They agree exactly at θ=0. At θ=π/2 their unique MAP decisions are sectors 1 and 3. KL(p₊||p₋) there is 3.0463766 nats. This proves a failure of identification from zero-rate support in a model class containing both functions. A specified physical sign convention and an explicitly implemented rotation, or a useful host inductive bias, may still produce a good zero-shot answer. This finite example does not estimate any host's error.

## Execution

Run `python check_f.py` in this directory to verify the witness and the parameter grid with the standard library. Run `python check_f.py --grid` to print the 22 planned conditions. The positive and negative rates are in radians per simulation step. Each row supplies phase factors for t₂=h, t₃=h+ell, and tₚ relative to t₁=0. A different reference origin requires re-expressing every factor. The stochastic Brownian phase is integrated or inferred; it never enters these features as a label. Trigonometric features computed from already public metadata cost no extra waveform-cache bits.

In one arm supply six zeros, and in the other the six derived phase components using an identical numeric projection, optimization schedule and parameter count. | Every arm sees nonzero rates during training. Evaluate on disjoint dev/test rates and fresh mothers. This estimates the incremental value of deterministic features under a matched supervision and parameter budget. Repeat with shared seeds. |

Use the same budget for the two host comparisons, recording any host-specific connector output dimensions and token counts. For the matched experiment, use 512 source mothers per training condition, 128 per development condition and 512 per new test condition with split-specific seeds 930101, 930202 and 930303. Within each split and timing configuration generate one set of independent unit-time Brownian increments, symbol draws and measurement noises per mother, then vary ω with those primitives fixed. Reuse these draws across both hosts and input arms. A transformed received third-window sector is a new target computed from the transformed observation; a change of prompt alone is a separate intervention. The historical C4 rate +0.35 is a known anchor on fresh data. Report ±0.55 separately as new rates. Restrict the primary comparison to the 2 dB, σφ=0.1 conditions in the grid. Report original C1/C2/C3 separately for forgetting. These counts specify a prospective protocol, not completed evaluations.

Primary endpoint is four-candidate NLL for Q3 repeat relative to same-cache direct readout, with accuracy and Q2-valid as secondary endpoints. Report host-minus-direct and phase-feature-minus-zero paired differences. Nest all rotations, rates and questions descended from one mother within the same bootstrap cluster when pooling. Include an independent-X3 control, scrambled cache, and a shuffled phase-feature control. If an explicit phase arm improves both hosts, attribute the measured gain to that interface under the specified training distribution. Neither these contrasts nor the frozen original baseline establish global Bayes optimality.

## Host preparation and resource status

Use the official Qwen snapshot for Qwen/Qwen3.5-4B. Record and pin its resolved commit before training. Stage 3 hard-codes the Mistral model loader, chat template and KV cache representation. A Qwen-specific wrapper must use its native tokenizer/template with thinking mode fixed, preserve the two window placeholders, keep connector gradients through the frozen text backbone and verify full-sequence candidate likelihoods before enabling any cache optimization. Score all four complete candidate continuations with the same protocol and list all four options for the separate generation endpoints. Run a forward/backward smoke test, then write checkpoints/results into a new run directory. The upstream --model-id option alone cannot implement this protocol.

The local interpreter exposes PyTorch 2.12.1+cpu, zero CUDA devices, and no installed transformers, accelerate or huggingface_hub. The inspected default Hub cache contains no Qwen snapshot. No GPU training execution connector was available. No host training, GPU timings or Qwen accuracy are claimed for this track. The historical Ministral run recorded 52,985.8 MB peak GPU memory at microbatch 32 and about 39 minutes for one connector. Qwen requirements depend on backbone, scorer, sequence length and microbatch and should be measured by its smoke test.
